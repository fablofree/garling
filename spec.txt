# Contexte et objectif

Agis comme un **Software Architect / Senior Backend Engineer avec 11+ années d’expérience**, spécialisé dans la conception d’API RESTful, l’architecture logicielle, PHP, MySQL, la sécurité applicative et les principes SOLID.

Je souhaite concevoir et développer un **Backend PHP RESTful API professionnel, maintenable, sécurisé et facilement déployable**, destiné à une application web de **gestion des équipements informatiques d’une ESN**.

L’API devra exposer l’ensemble de ses endpoints sous la racine :

`/api`

Les réponses de l’API devront être exclusivement au format **JSON**, avec une structure cohérente et standardisée pour les réponses de succès, d’erreur et de validation.

Le backend devra respecter les exigences suivantes :

* **PHP** orienté objet (POO)
* Architecture **MVC**
* Application stricte des principes **SOLID**
* Architecture modulaire et facilement extensible
* Séparation claire des responsabilités
* API **RESTful**
* Format d’échange **JSON**
* Authentification basée sur **JWT (JSON Web Token)**
* Gestion centralisée des erreurs et exceptions
* Validation des données entrantes
* Protection contre les injections SQL via des requêtes préparées
* Hashage sécurisé des mots de passe
* Configuration externalisée
* Code propre, lisible et maintenable
* Éviter autant que possible les dépendances inutiles

L’architecture devra notamment séparer clairement les responsabilités entre :

* `Model`
* `Controller`
* `Repository`
* `Service`
* `Core`
* `Config`
* `Middleware`
* `Database`
* `Routes`
* `Utils` ou composants transverses si nécessaire

Propose une organisation de projet professionnelle, cohérente avec les bonnes pratiques utilisées dans des projets backend en entreprise.

# 5. Authentification et sécurité

L'API doit utiliser **JWT** pour sécuriser les endpoints.

Le fonctionnement attendu est le suivant :

### Endpoint public

Seul :

`POST /api/login`

est accessible sans token.

Tous les autres endpoints doivent nécessiter un JWT valide.

Le middleware d'authentification devra :

1. récupérer le token depuis le header HTTP ;
2. vérifier sa présence ;
3. vérifier son format ;
4. vérifier sa signature ;
5. vérifier son expiration ;
6. authentifier l'utilisateur ;
7. transmettre les informations nécessaires au contrôleur.

Utiliser le format HTTP standard :

`Authorization: Bearer <token>`

En cas d'absence ou d'invalidité du token, retourner une réponse JSON appropriée avec le code HTTP correspondant.

Les mots de passe ne doivent **jamais être stockés en clair**.

Utiliser les mécanismes sécurisés de PHP tels que :

`password_hash()`

et

`password_verify()`.

# 6. Format standard des réponses API

Définir un format homogène pour toutes les réponses.

Par exemple :

Succès :

```json
{
  "success": true,
  "message": "Opération effectuée avec succès",
  "data": {}
}
```

Erreur :

```json
{
  "success": false,
  "message": "Une erreur est survenue",
  "errors": []
}
```

Les codes HTTP REST appropriés devront être utilisés :

* `200` : succès
* `201` : ressource créée
* `204` : suppression réussie sans contenu
* `400` : requête invalide
* `401` : non authentifié
* `403` : accès interdit
* `404` : ressource inexistante
* `422` : erreur de validation
* `500` : erreur serveur

# 18. Qualité du code

Le code doit respecter les principes suivants :

* Single Responsibility Principle ;
* Open/Closed Principle ;
* Liskov Substitution Principle ;
* Interface Segregation Principle ;
* Dependency Inversion Principle.

Éviter :

* les Controllers contenant toute la logique métier ;
* les requêtes SQL directement dans les Controllers ;
* les classes trop volumineuses ;
* les dépendances circulaires ;
* le code dupliqué ;
* les variables globales ;
* les secrets dans le code source.

Favoriser :

* l'injection de dépendances ;
* les interfaces lorsque pertinent ;
* les services métier ;
* les repositories ;
* les composants réutilisables ;
* une gestion centralisée des réponses HTTP ;
* une gestion centralisée des exceptions.
